kubectl, in context

A practical reference for investigating workload problems. Each command answers a question, and each result points to a useful next check.

Replace example names with the values from your environment. Confirm the current context before running commands. Command output below is illustrative.

Orient yourself

Read only

Confirm the cluster and locate the affected workload before investigating details.

Check the active context

Am I connected to the intended cluster?
kubectl config current-context

Look for: the expected cluster and account in the context name.

Find pods and node placement

Which pods are affected, and where are they running?
kubectl get pods -n interview -o wide

Look for: readiness, restart count, age, status, and the assigned node.

Inspect a pod

Read only

Events, conditions, and the admitted pod specification help separate scheduling problems from container setup problems.

Read conditions and events

What is preventing the pod from becoming ready?
kubectl describe pod scanner-abc -n interview

Look for: FailedScheduling, image pull errors, probe failures, mount errors, and container waiting or termination reasons.

Illustrative event output
Warning  FailedScheduling  default-scheduler  0/4 nodes are available: 2 Insufficient memory.

Next: If no node is assigned, inspect resource requests and placement rules. If a node is assigned, follow setup events such as image, volume, or sandbox failures.

Inspect the admitted configuration

What settings did Kubernetes receive?
kubectl get pod scanner-abc -n interview -o yaml

Look for: spec.nodeName, requests and limits, probes, node selectors, tolerations, images, and volume references.

Read container logs

Read only

Use the container name and time window to focus on the failure you are investigating.

Read recent logs

What did the application report before the issue?
kubectl logs scanner-abc -n interview -c worker --since=10m --tail=100 --timestamps

Look for: startup errors, failed dependency calls, and timestamps that match the incident.

Read the previous container instance

What happened before the restart?
kubectl logs scanner-abc -n interview -c worker --previous --tail=100

Look for: the last error before termination. Previous logs cover the prior instance of that container, when available.

Check a Service

Read only

Compare the Service selector and ports with its EndpointSlices and the pods behind them.

List Services and EndpointSlices

Does the Service have ready backends?
kubectl get services,endpointslices -n interview

Look for: expected addresses, ports, and endpoint readiness. Then compare the Service selector with pod labels.

Next: If the endpoints look right, test DNS and connectivity from the same network context as the failing client. A listed endpoint alone does not establish that the request succeeds.

Check capacity

Read only

Use live usage as one clue. Scheduling decisions depend on requests and eligible node capacity.

Inspect node conditions and requests

Is a node under pressure or fully requested?
kubectl describe node worker-1

Look for: Ready and pressure conditions, taints, allocatable resources, and the allocated requests summary.

Check recent pod usage

What CPU and memory are pods using now?
kubectl top pods -n interview --containers

Look for: unusually high or changing usage. This command needs the resource metrics API; it does not show what the scheduler has reserved.

Verify a rollout

Read only

Check controller progress and application health after a deployment or mitigation.

Wait for Deployment progress

Has the Deployment completed its rollout?
kubectl rollout status deployment/scanner -n interview --timeout=120s

Look for: the success message or the specific condition that is still blocking progress.

Review available revisions

What rollout history is available?
kubectl rollout history deployment/scanner -n interview

Look for: revision numbers and change history. Rollback is a workload change; confirm the target revision and deployment source before using it.

Roll back to a known-good revision

Use only when rollback is authorized and suitable.
kubectl rollout undo deployment/scanner -n interview --to-revision=2

Afterward: check rollout status, Ready replicas, and the customer operation. Rollback may not restore separately changed configuration or external dependencies.
